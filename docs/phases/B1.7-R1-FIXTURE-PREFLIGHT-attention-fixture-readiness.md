## 7. Locked Attention lifecycle

Authoritative statuses are:

- `open`

- `acknowledged`

- `resolved`

- `dismissed`

- `expired`

Terminal statuses are:

- `resolved`

- `dismissed`

- `expired`

Archive is orthogonal lifecycle metadata through:

`archived_at`

Archive is **not** an Attention status.

### Allowed operational transitions

```text

open -> acknowledged

open -> resolved

open -> dismissed

acknowledged -> resolved

acknowledged -> dismissed

```

Expiration remains system/rule-owned.

### Explicit exclusions

R1 does not introduce:

- reopen;

- restore;

- snooze;

- alternate close status;

- priority field;

- multi-assignee;

- autonomous lifecycle decisions.

A fixture implementation must not invent any of these capabilities.

### Archive boundary

Only terminal, non-archived Items may be archived.

Open or acknowledged Items cannot be archived.

Archived Items cannot receive later operational mutations.

There is no Attention restore path in R1.

## 9. Assignment contract

Attention supports one assignee or no assignee.

`null` means unassigned.

No multi-assignee behavior exists.

A valid assignment target must:

- have an existing organization membership;

- have an **active** membership;

- belong to the **same organization** as the Attention Item.

The following targets must be rejected:

- suspended member;

- removed/non-active member;

- member of another organization;

- malformed member identifier;

- nonexistent member identifier;

- foreign-tenant member.

Expected later fixture verification includes:

- assign to controlled active same-org QA member;

- unassign;

- same-assignee safe no-op behavior;

- suspended target rejection;

- foreign-target rejection;

- Viewer mutation denial;

- Staff allowed assignment but denied Archive.

Fixture preparation may not weaken the assignment contract for convenience.
