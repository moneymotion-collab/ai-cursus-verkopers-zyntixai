## 2. Problem statement

B1.7.4 delivered a Progress-shaped Attention **application foundation** (typed read models, org-scoped queries, mappers, RPC adapters, protected path, hidden AppShell wiring) and deliberately shipped **no** product workspace.

Without a dedicated B1.7.5 contract, implementers risk:

- enabling navigation before loading/empty/error/unavailable states exist;
- mixing B1.7.6 mutation UX into the first visible Attention surface;
- bypassing B1.7.4 read queries with ad-hoc Supabase calls;
- inventing filters or sorts outside the B1.7.4 allowlist.

---

## 3. Goal (testable)

Deliver a **read-only**, Progress-shaped Attention Workspace & Detail UX so that an authenticated active organization member can:

1. open `/attention` and browse organization-scoped Attention Items via the B1.7.4 read layer;
2. filter, sort, and paginate using **existing** B1.7.4 contracts only;
3. open `/attention/[attentionItemId]` for read-only detail, signals, and immutable event timeline;
4. see role-correct archived visibility according to B1.7.4 permissions;
5. discover Attention in AppShell **only after** the minimum workspace chain is proven (subphase E);
6. optionally reach Attention from Enrollment via existing read-layer capabilities only;
7. never see working lifecycle mutation controls in this phase.

## 8. Sorting decision (owner-corrected)

### Keep B1.7.4 defaults unchanged

The B1.7.4 Zod/API defaults remain authoritative and **must not** be changed by B1.7.5:

- supported sort fields: `created_at` | `updated_at` | `severity` | `last_detected_at`
- default field: `created_at`
- default direction: `desc`
- stable secondary tie-break: `id` (foundation)

### Desired Attention list UX order

1. most recently detected Attention first → request sort field **`last_detected_at`** direction **`desc`**;
2. rely on the existing stable server-side tie-breaker;
3. **no** unstable client-side re-sorting after pagination.

### Feasibility

`last_detected_at` is already a supported B1.7.4 sort enum value (`attentionSortSchema` / B1.7.4 query contract). Therefore:

- B1.7.5 list loaders/UI **must explicitly request** `{ field: "last_detected_at", direction: "desc" }` (or equivalent validated input);
- omitting sort must not silently depend on a changed foundation default;
- no B1.7.4 schema edit is required for this decision;
- no blocking dependency or contract gap remains for sort support.

### Archived visibility (authoritative)

## 13. Uniform unavailable behavior

Use the existing uniform unavailable result for:

- non-existent records;
- cross-tenant records;
- archived-not-allowed records;
- otherwise inaccessible records.

The UI must **not** reveal distinctions that would let a user infer:

- that a record exists in another tenant;
- that an archived record exists;
- that an ID is valid but inaccessible;
- which organization or user is attached.

Prefer a uniform **Attention unavailable** panel over distinguishable 404 semantics for authenticated access checks.

## 14. Error, loading, and empty states

| Condition | UX |
| --- | --- |
| No org / no membership / suspended / unknown role | Full-page organization unavailable / denied |
| Missing / foreign / unauthorized / archived-for-role item | Uniform unavailable panel |
| Invalid UUID route param | Unavailable / validation error — not raw exception |
| Invalid filters / pagination / sort in querystring | Coerce to safe defaults or show validation error; never raw Zod dump |
| Database/application error | Safe error state + retry where appropriate; never raw DB/RPC text |
| Unauthenticated | Middleware redirect to `/login?next=…` |

### Empty

| Case | Behavior |
| --- | --- |
| Org has zero Attention items | Empty workspace copy — **no create CTA** |
| Filters match nothing | No-results + clear-filters |
| Item has zero signals | Empty signals section |
| Missing optional relations | Section omitted or safe “Unavailable” / “Unknown” label |

## 15. Accessibility and responsive UX

### Accessibility (acceptance)

1. Semantic `h1`/`h2` hierarchy on list and detail.
2. Keyboard access to filters, links, pagination.
3. Visible focus states.
4. Labeled filter controls.
5. Status/severity have text (and `aria-label` if icon used).
6. Color is never the only status/severity cue.
7. Tables (if used) have headers; otherwise list semantics.
8. Rows are links/buttons — not clickable non-focusable `div`s.
9. Timeline has list/order semantics.
10. Loading/error announcements where Progress patterns do.
11. Contrast sufficient for text/badges.
12. Touch targets usable on mobile.
13. Filter apply does not drop focus unrecoverably.
14. Honor `prefers-reduced-motion` if motion is added.

### Responsive

| Viewport | Requirements |
| --- | --- |
| Desktop | Filters + list readable; detail multi-section |
| Tablet | Reflow filters; no overflow |
| Mobile ~390×844 | Single column; status/severity visible; pagination reachable; timeline readable; breadcrumbs usable |
