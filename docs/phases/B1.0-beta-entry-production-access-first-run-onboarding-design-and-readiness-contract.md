## 4. Current Authentication Architecture

### 4.1 End-to-end flow (as implemented)

```text
Unauthenticated /
  → redirect /login                          (src/app/page.tsx)

/login (unauthenticated)
  → LoginForm → loginAction → signInWithPassword
  → if !email_confirmed_at → /register/check-email
  → else resolvePostLoginDestination → product or /register/complete

/register (flag true only)
  → registerAction → signUp(email, password, metadata display_name/company_name)
  → always /register/check-email (enumeration-safe)
  → handle_new_user creates profiles + optional registration_intents

Email link → /auth/callback?code=…
  → exchangeCodeForSession
  → tryProvisionAndLand → complete_owner_self_registration RPC
  → /leads?org=<id> or /register/complete

Authenticated /
  → resolveAuthenticatedEntryPath
  → product landing if memberships exist
  → else check-email or /register/complete

Protected /leads|/customers|/tasks
  → middleware requires user
  → unverified email redirected to /register/check-email
```

### 4.2 State behavior matrix (current code)

| State | Actual behavior | Evidence |
| --- | --- | --- |
| Unauthenticated visitor on `/` | Redirect `/login` | `src/app/page.tsx` |
| Unauthenticated on protected path | Redirect `/login?next=…` (+ `reason=session_expired` if auth cookie present) | `src/lib/supabase/middleware.ts` |
| Authenticated on `/login` | Middleware → `/`; page also redirects via `resolvePostLoginDestination` | middleware + `login/page.tsx` |

## 5. Production Login Risk Analysis

Observed historical symptom (starting context, **not re-proven in B1.0**): localhost login succeeds; production returns invalid email/password messaging.

App maps many Auth failures (including HTTP 400) to `"Invalid email or password."` (`normalize-auth-error.ts`). That message is therefore **ambiguous** and can mask configuration, confirmation, or project-mismatch failures.

### Proven facts (repository)

1. Login uses `signInWithPassword` against whatever project `NEXT_PUBLIC_SUPABASE_URL` + publishable key resolve to (`auth-actions.ts`, `getPublicSupabaseEnv`).
2. Required client-visible env vars throw if missing (`src/lib/env/public.ts`) — fail-closed for URL/key presence.
3. `PUBLIC_REGISTRATION_ENABLED` is server-only, fail-closed (`parsePublicRegistrationEnabled` accepts only exact `true`).
4. Callback email redirect origin is built from `NEXT_PUBLIC_SITE_URL`, else `VERCEL_URL`, else `http://127.0.0.1:3000` (`siteOrigin()` in `auth-actions.ts`).
5. `.env.example` documents public Supabase vars and `PUBLIC_REGISTRATION_ENABLED=false`; it does **not** document `NEXT_PUBLIC_SITE_URL` even though registration/resend depend on it.
6. Local `supabase/config.toml` redirect allowlist is localhost-only.
7. Production Auth settings, Vercel env values, and live login outcomes were **not** inspected or mutated in B1.0.

### Strong evidence

| Rank | Cause | Why likely |
| --- | --- | --- |
| 1 | Production Auth user does not exist / wrong project keys | Local and hosted are different Supabase projects; same email may only exist locally. |
| 2 | Email not confirmed in hosted Auth | App and local config expect confirmations; unconfirmed users are redirected to check-email after a successful session, but hosted may reject login depending on Auth settings — either path can present as “cannot use product.” |
| 3 | Redirect / Site URL misconfiguration | Confirmation links built with wrong origin (`siteOrigin` fallback) or hosted allowlist missing production `/auth/callback`. |
| 4 | Credential / password not the production account | Support ambiguity amplified by generic invalid-credentials mapping. |

### Hypotheses

| Rank | Cause | Notes |
| --- | --- | --- |
| 5 | Preview deployment using ephemeral `VERCEL_URL` while Auth allowlist only has production domain | Would break confirmation more than password login. |
| 6 | Publishable key / URL typo in Vercel Production vs Preview | Would break both register and login. |
| 7 | Case/normalization differences | App lowercases email on register/login schemas — less likely if both use app forms. |

### Unavailable evidence (must be collected in B1-R1)

- Hosted Supabase Auth: confirmations, Site URL, redirect allowlist, signup enabled.
- Vercel Production env: presence (not values) of `NEXT_PUBLIC_SUPABASE_*`, `NEXT_PUBLIC_SITE_URL`, `PUBLIC_REGISTRATION_ENABLED`.
- Browser proof: same approved test account on local vs production.
- Auth logs for failed production login (without storing secrets).

**Do not mark production login PASS without that proof.**

## 6. Registration and Provisioning Contract

### 6.1 Intended lifecycle (current + B1 continuation)

```text
1. Gate: PUBLIC_REGISTRATION_ENABLED === "true" (else fail-closed)
2. Validate: name, email, password, companyName (register-schema.ts)
3. Auth user created: supabase.auth.signUp (+ user_metadata display_name, company_name)
4. Before confirmation:
   - handle_new_user → profiles row
   - registration_intents pending (if metadata present)
   - No organization / membership
   - Product routes blocked for unverified users
5. After confirmation (/auth/callback or /register/complete):
   - ensureRegistrationIntent
   - complete_owner_self_registration(p_name, p_slug)
   - Creates organizations + organization_members(role=owner, status=active)
   - Marks registration_intents completed
   - Optional profiles.display_name update
6. Land: /leads?org=<organizationId>
7. B1 addition: if onboarding incomplete → /onboarding before product workspaces
```

### 6.2 Operation ownership

| Artifact | Created by |
| --- | --- |
| Auth user | `registerAction` → `signUp` |
| Profile | DB trigger `handle_new_user` |
| Registration intent | `handle_new_user` and/or `upsert_registration_intent` |
| Organization | RPC `complete_owner_self_registration` |
| Owner membership | Same RPC (constant role `owner`) |

### 6.3 Idempotency and failure

| Scenario | Contract (implemented) |
| --- | --- |
| Repeated callback | Membership guard + intent completed → return existing org; advisory lock prevents dual org |
| Slug collision | App retries with suffix (`MAX_SLUG_ATTEMPTS`); unique_violation keeps intent pending |
| Partial failure | Org+member insert in subtransaction; intent remains pending/failed for retry via `/register/complete` |
| Duplicate orgs | Prevented for self-registration path when grants/hardening hold; legacy `create_organization_with_owner` EXECUTE revoked from `authenticated` |
| Flag absent/malformed | Registration disabled |

### 6.4 Active organization resolution

- Listing: `listActiveOrganizationMemberships` — active memberships for `auth.uid()` only.
- Scoped workspaces: `resolveOrganizationContext` requires membership match to requested org id; does not trust arbitrary client org without membership.
- Landing: single membership → `/leads?org=…`; multi → `/leads` (selector in AppShell).

### 6.5 B1 extension point

After successful provisioning (membership exists), B1 inserts an **onboarding gate** before treating the user as fully entered. Provisioning completion ≠ product onboarding completion.

## 8. Onboarding Completion Contract

### Authoritative rule

```text
Organization onboarding is complete iff
organizations.onboarding_completed_at IS NOT NULL
for the active organization resolved from the caller’s membership.
```

- Server-authoritative (set only by authenticated server action after validating required fields).
- Tenant-scoped (update only org where caller has active `owner` or `admin` membership; prefer **owner-only** for beta write of completion).
- Idempotent: re-submit when already completed returns success without changing the original timestamp.
- Safe across refresh / multi-tab / retry: completion is a single nullable timestamptz; writes use membership-checked UPDATE.
- Auditable: timestamp is enough for beta support; optional `updated_at` already exists on organizations.
- Impossible to complete for another organization: organization id taken from resolved membership context, never trusted solely from client body.

### Behavioral table

| Situation | Behavior |
| --- | --- |
| Close halfway | Partial field updates may persist if step-save is implemented; completion remains null → next login returns to `/onboarding` |
| Refresh | Resume from server-loaded org/profile values |
| Logout halfway | Incomplete; next login → onboarding |
| Return later | Same |
| Fields entered at registration | Prefill name/company; still require steps 2–3 enums before completion |
| Existing production user predating onboarding | `onboarding_completed_at` null → force onboarding once (backfill strategy: null means incomplete) |
| Owner in multiple orgs | Gate per selected/active org; completing org A does not complete org B |
| Older org missing new required enums | Onboarding form requires them before completion |

**Do not** treat `registration_intents.status = completed` as product onboarding complete.

- Avoid loops: `/onboarding` must not redirect to itself; completion → fixed product fallback **`/leads`** (existing primary CRM surface; no invented dashboard).

- Registration flag never disables login, logout, callback, or recovery.
- Deterministic post-onboarding destination: `/leads?org=<activeOrgId>` when single membership; `/leads` when multi.

## 11. Security Contract

### Mandatory rules for B1 implementation

1. All onboarding writes via server actions / route handlers with `auth.getUser()`.
2. Authorize via active `organization_members` for the target org; prefer owner (admin optional) for onboarding completion.
3. Never trust client-supplied organization id without membership resolution.
4. Preserve RLS tenant isolation; no service-role key in client bundles.
5. Use Next.js server actions (same CSRF model as existing auth actions).
6. Zod validation; strict enums; length limits; control-char rejection.
7. Idempotent completion; duplicate-submit guards in UI (`pendingRef` pattern already used).
8. Registration callback replay remains safe (existing RPC); onboarding completion must be equally safe.
9. Partial registration remains on `/register/complete`; do not weaken email confirmation gates.
10. No admin/service keys in client code; no credentials in logs; no secrets in URLs.
11. Redirects only via `resolveSafeReturnPath` allowlist; extend allowlist for `/onboarding` and recovery paths explicitly.
12. `PUBLIC_REGISTRATION_ENABLED` remains fail-closed; must not affect login/logout/recovery.
13. User-safe errors only; map internals like existing `normalize-*-error` helpers.

### Current conflicts / gaps vs this contract

| Issue | Severity | Notes |
| --- | --- | --- |
| No password recovery | High for beta support | Must address in B1.1 |
| No onboarding authorization surface yet | Expected | To implement |
| `normalizeLoginError` treats many `status === 400` as invalid credentials | Medium | Can hide production misconfig; consider narrower mapping later without leaking internals |
| `.env.example` omits `NEXT_PUBLIC_SITE_URL` | Medium | Document in B1.1 |
| Lead empty state lacks first-action CTA | Low | B1.4 |
| Multi-org onboarding not gated today | N/A until onboarding ships | Define per-org gate |

No evidence of service-role usage in auth UI paths from registration security tests (`tests/security/registration-source-security.test.ts`).

## 13. Migration Decision

```text
Small additive migration required.
```

Existing `profiles.display_name` and `organizations.name` / `locale` / `timezone` are insufficient for business-type personalization and authoritative onboarding completion.

### Proposed migration (do **not** write in B1.0)

**Filename pattern:** `supabase/migrations/YYYYMMDDHHMMSS_add_organization_first_run_onboarding.sql`

**Columns on `public.organizations`:**

| Column | Type | Null | Default | Notes |
| --- | --- | --- | --- | --- |
| `business_type` | `text` | yes until complete | null | CHECK IN enum list |
| `primary_audience` | `text` | yes | null | CHECK |
| `primary_offering` | `text` | yes | null | CHECK |
| `primary_goal` | `text` | yes | null | CHECK |
| `team_size_band` | `text` | yes | null | CHECK optional |
| `onboarding_completed_at` | `timestamptz` | yes | null | Authoritative completion |
| `first_run_checklist_dismissed_at` | `timestamptz` | yes | null | Checklist dismiss |

**Constraints:** CHECK constraints for enums; optional CHECK that if `onboarding_completed_at IS NOT NULL` then required enums/name non-null (enforce in app and/or DB).

**Indexes:** none mandatory beyond PK; optional partial index on `onboarding_completed_at IS NULL` only if ops need it (skip for beta).

**RLS:** reuse `organizations_update_admin` (owner/admin). No new table ⇒ no new policies required unless completion must be owner-only (then add tighter policy or enforce in SECURITY DEFINER RPC).

**Grants:** unchanged (`select, update` to authenticated already).

**Backfill:** leave `onboarding_completed_at` null for all existing orgs → forces one-time onboarding (safest for beta personalization). Do **not** auto-complete from registration alone.

**Rollback:** additive nullable columns are droppable in a follow-up migration if abandoned; no destructive rewrite.

**Idempotency:** migration should use `add column if not exists` patterns only if repo convention allows; otherwise standard single-apply Supabase migration.
