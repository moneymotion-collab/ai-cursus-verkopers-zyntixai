## 2. Problem statement

After B1.7.3 the platform has Attention schema, SELECT RLS, SECURITY DEFINER mutation RPCs, role/tenant fail-closed checks, audit events, and typed domain helpers under `src/features/attention/domain/*`.

Still **not** usable as an application foundation:

- no organization-scoped Attention read models / repositories;
- no server query adapters for list/detail/signals/events;
- no membership-resolved Attention page organization helper;
- no RPC adapters wrapping B1.7.3 public RPCs;
- no safe-return / protected-path wiring for `/attention*`;
- no AppShell Attention navigation registration (even hidden).

Risk of skipping this phase:

- UI that bypasses membership org resolution or fail-closed unavailable shapes;
- dashboard / NBA / automation without read foundations;
- mixing list UX, mutation UX, and adapters into one unsafe mega-phase.

## 4. Architecture contract

### Required layer stack

```text
Supabase tables (attention_items / attention_signals / attention_item_events)
        ↓  authenticated client SELECT under existing RLS
organization-scoped repository / read queries
        ↓
database-to-domain mapping (map-attention-read-model)
        ↓
application service / server adapters (+ RPC adapters for mutations)
        ↓
typed AttentionResult / AttentionApplicationError contracts
        ↓
later B1.7.5 / B1.7.6 UI (out of scope here)
```

### Layer separation (mandatory)

| Layer | Responsibility | Must not |
| --- | --- | --- |
| Generated DB types | `src/types/database.generated.ts` Attention tables/RPCs | Drive UI directly |
| DB row shapes | Query column selects | Leak into React components |
| Domain models | `src/features/attention/domain/*` + new read types | Call Supabase |
| Repository / read queries | Org-scoped list/get/events/signals | Direct INSERT/UPDATE/DELETE |
| Application / service contracts | Result unions, permissions | Trust client org id |
| RPC mutation adapters | Wrap B1.7.3 RPCs only | Invent new lifecycle SQL |
| Future UI | B1.7.5+ | Call tables/RPCs bypassing adapters |

React components must **not** call Attention tables or RPCs directly when this repository pattern is in place.

## 10. Query contracts

All reads: authenticated Supabase client + membership-resolved org + explicit `organization_id` filter + existing RLS. **No service role.**

### 10.1 `listAttentionItems`

| Aspect | Contract |
| --- | --- |
| Input | `{ organizationId, filters?, sort?, pagination? }` |
| Output | `{ items: AttentionListItemReadModel[]; pagination: PaginationMeta }` or fail |
| Org scoping | membership-resolved; client org id alone insufficient |
| Auth | active owner/admin/staff/viewer; suspended / none / other tenant → unavailable / denied |
| Default archived | exclude `archived_at IS NOT NULL`; owner/admin may set `includeArchived: true` |
| Filters (technical; no UX) | `status`, `severity`, `assigneeMemberId`, `enrollmentId`, `customerId`, `programId`, `acknowledged` (true/false), `createdFrom`/`createdTo`, `updatedFrom`/`updatedTo` |
| Sort | `created_at` \| `updated_at` \| `severity` \| `last_detected_at`; default newest `created_at` desc; secondary `id` asc |
| Pagination | required bounded page size (Progress-style defaults/limits; reject unbounded) |
| Empty | `ok: true` with empty items |
| Errors | auth / org unavailable / invalid input / database / unexpected |

### 10.2 `getAttentionItemById`

| Aspect | Contract |
| --- | --- |
| Input | `{ organizationId, attentionItemId }` |
| Output | detail read model **or** uniform unavailable |
| Not found / other tenant / unauthorized | same unavailable shape (no existence leak) |
| Archived | visible to owner/admin; members → unavailable if archived |

### 10.3 `listAttentionEventsForItem`

| Aspect | Contract |
| --- | --- |
| Input | `{ organizationId, attentionItemId }` (optional pagination if volume warrants) |
| Output | ordered event read models |

## 12. Result and error contract

Reuse the Progress application pattern (authoritative in-repo), Attention-prefixed:

```ts
type AttentionApplicationError = {
  code: AttentionApplicationErrorCode;
  message: string;
  retryable: boolean;
  category:
    | "auth"
    | "permission"
    | "validation"
    | "not_found"
    | "conflict"
    | "network"
    | "server";
  fieldErrors?: Record<string, string>;
  cause?: string;
};

type AttentionReadQueryResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: AttentionApplicationError };

type AttentionRpcAdapterResult<T = void> =
  | { ok: true; data?: T }
  | { ok: false; error: AttentionApplicationError };
```

Minimum error codes:

- `AUTH_REQUIRED`
- `ORG_CONTEXT_MISSING`
- `INVALID_INPUT`
- `ATTENTION_ITEM_UNAVAILABLE` (uniform not-found / unauthorized / cross-tenant)
- `ENROLLMENT_UNAVAILABLE`
- `PERMISSION_DENIED` / `INSUFFICIENT_ROLE`
- `INVALID_STATE` / conflict-class codes mirroring RPC messages where safe
- `NETWORK_ERROR` / `DATABASE_UNAVAILABLE` / `UNEXPECTED_ERROR`

Client-facing messages must not distinguish cross-tenant existence. Log `cause` server-side only where appropriate.

Do **not** invent a parallel `ok:false; error: "not_found"` string-literal union if the Progress structured error pattern is available.
