## 7. Official object model (locked)

```text
MODEL B — Attention Signal + Attention Item
```

### Attention Signal

Immutable, auditable detection/evidence record:

- describes what was detected;
- references underlying source;
- carries evidence;
- carries `detected_at` and rule/actor info;
- is **not** content-overwritten;
- may be added again on repeated detection.

### Attention Item

Operational follow-up unit in the Attention Workspace:

- groups relevant Signals;
- has lifecycle, severity, assignee;
- can be acknowledged;
- can be resolved, dismissed, or expired;
- remains explainable via evidence and history;
- may later feed a separate NBA phase (not in B1.7).

Do **not** duplicate Tasks, Progress, or Enrollments. Do **not** use product name “Case” in R1 UI.

### Stale-progress threshold (locked)

```text
14 calendar days, computed in UTC
```

| Rule | Contract |
| --- | --- |
| Evaluable Enrollment | Non-archived; status in `{active, paused}` (statuses that retain Progress-recording eligibility under Progress contracts). `pending` / `completed` / `cancelled` / archived: **do not** open new Items from this rule in R1 |
| Reference timestamp | `max(occurred_at)` among **non-voided** Progress facts for that Enrollment |
| Fallback when no non-voided Progress | Enrollment `created_at` (UTC) |
| Clock | **Server-side only**; client time not authoritative |
| Idempotency | Repeated evaluate must not create a second **non-terminal** Item for the same dedupe key |
| Repeated detection | Append immutable Signal and/or update `last_detected_at` / detection count per §14 |
| Threshold config | Platform default in R1 — **no** org config UI; future org override allowed only under later approval |

### Rule evaluation path (locked)

**Primary:** controlled server-side scheduler / scheduled evaluation path.

**Secondary:** Owner/Admin manual re-evaluation invoking the **same** authoritative logic.

| Constraint | Requirement |
| --- | --- |
| Scope | Organization-scoped |
| Idempotent | Yes |
| Auditable | Yes |
| Client-authoritative evaluate | Forbidden |
| Service-role | No bypass without explicit org validation |
| Failures | Observable |
| Staff/Viewer manual re-eval | **No** in R1 |
| Implementation in B1.7.0 | **None** — design only |

## 11. Lifecycle (locked)

Statuses: `open` | `acknowledged` | `resolved` | `dismissed` | `expired`.

Authoritative flow:

```text
open → acknowledged → resolved | dismissed | expired
```

Also allowed for create/terminal handling:

| From | To | Notes |
| --- | --- | --- |
| (create) | `open` | Manual or rule creates Item |
| `open` | `resolved` \| `dismissed` \| `expired` | Skip acknowledge when justified |
| `acknowledged` | `resolved` \| `dismissed` \| `expired` | Normal path |

| Hard rule | |
| --- | --- |
| Terminal | `resolved`, `dismissed`, `expired` |
| Reopen | **Out of R1** |
| Snooze | **Out of R1** |
| Silent reopen | Forbidden |
| New issue after terminal | New Item allowed under dedup (§14) |
| Validation | Server-side only |
| History | Required for every transition |

### Transition matrix

| From | To | Roles | Required | Reason required |
| --- | --- | --- | --- | ---: |
| — | `open` | owner/admin/staff (manual); system/rule | title + enrollment | No |
| `open` | `acknowledged` | owner, admin, staff | — | No |
| `open` | `resolved` | owner, admin, staff | resolution reason | **Yes** |
| `open` | `dismissed` | owner, admin, staff | dismissal reason | **Yes** |
| `open` | `expired` | system/rule only | policy ref | No |
| `acknowledged` | `resolved` | owner, admin, staff | resolution reason | **Yes** |
| `acknowledged` | `dismissed` | owner, admin, staff | dismissal reason | **Yes** |
| `acknowledged` | `expired` | system/rule only | policy ref | No |
| terminal | any | — | — | **Denied** |

### Resolution vs dismissal vs expiration

| Type | Meaning | Reporting / future NBA |
| --- | --- | --- |
| Resolved | Concern handled or objectively gone | Closed success; not an open attention feed for NBA |
| Dismissed | No further ops follow-up by decision | Closed by judgment; NBA must **not** treat dismiss as “problem solved” evidence without separate product rules later |
| Expired | Time-bound relevance ended | Closed by policy; may re-open as **new Item** if problem returns |

Dismissal is **not** silent deletion.

## 15. Deduplication (locked)

```text
At most one non-terminal Attention Item per
organization_id + enrollment_id + signal/rule key
```

| Event | Behavior |
| --- | --- |
| Repeated detection while non-terminal | No second open Item; append immutable Signal; may update `last_detected_at` / detection count; evidence stays auditable |
| Concurrency | Database-side unique constraint / upsert for open dedupe key |
| After terminal | New incident **may** create a **new** Item (new open lifecycle) when rule/manual detects again |
| Manual title collision on same Enrollment | Prefer attach Signal to existing non-terminal Item |

Rule key for `enrollment_no_recent_progress` = that rule id. Manual key = stable normalized key derived from Enrollment + manual signal type (implementation detail in B1.7.1/2).

## 19. Conceptual data model (no SQL)

Minimum Item fields: id, organization_id, enrollment_id, customer_id, program_id, title, summary, status, severity, assignee_member_id, dedupe_key, detection_count, first_detected_at, last_detected_at, acknowledged_at, resolved_at, dismissed_at, expired_at, resolution_reason, dismissal_reason, archived_at, created_by_member_id, updated_by_member_id, created_at, updated_at.
