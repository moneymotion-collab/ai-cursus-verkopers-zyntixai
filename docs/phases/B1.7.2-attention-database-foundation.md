## 10. Item schema

Columns: `id`, `organization_id`, `enrollment_id`, `customer_id`, `program_id`, `title`, `summary`, `status`, `severity`, `assignee_member_id`, `dedupe_key`, `detection_count`, `first_detected_at`, `last_detected_at`, `acknowledged_at`, `resolved_at`, `dismissed_at`, `expired_at`, `resolution_reason`, `dismissal_reason`, `archived_at`, `created_by_member_id`, `updated_by_member_id`, `created_at`, `updated_at`.

Notes:

- `customer_id` / `program_id` are denormalized **Enrollment participation context** for same-org composite FK integrity (matches B1.7.0/B1.7.1 and progress-facts pattern). They are not independent Attention sources.
- No `priority`, snooze, reopen, polymorphic `source_type`/`source_id`.
- `updated_at` maintained via existing `public.set_updated_at()` trigger.

---

## 11. Signal schema

Columns: `id`, `organization_id`, `attention_item_id`, `enrollment_id`, `signal_origin`, `rule_key`, `explanation`, `evidence` (jsonb object), `detected_at`, `created_by_member_id`, `created_at`.

No lifecycle/status, severity-as-state, assignee, `archived_at`, or general update flow.

---

## 12. Status constraint

`status in ('open','acknowledged','resolved','dismissed','expired')` via CHECK.  
`archived` is **not** a status.

---

## 13. Severity constraint

`severity in ('low','medium','high','critical')` via CHECK. No numeric score; no priority column.

---

## 14. Lifecycle constraints

Per-status field CHECKs enforce:

- `open`: no terminal timestamps/reasons; no `acknowledged_at`
- `acknowledged`: requires `acknowledged_at`; no terminal reasons
- `resolved`: requires `resolved_at` + non-empty `resolution_reason`
- `dismissed`: requires `dismissed_at` + non-empty `dismissal_reason`
- `expired`: requires `expired_at`; no resolve/dismiss reasons
- Reasons only allowed on their terminal statuses

Active membership / role transitions remain B1.7.3 RPC concerns.

---

## 15. Archive contract

- Soft-archive via `archived_at` only
- CHECK: `archived_at` allowed only when status ∈ `{resolved,dismissed,expired}`
- No hard-delete product path; no restore in R1

---

## 16. Assignment relation

`assignee_member_id` nullable; composite FK to `organization_members (organization_id, id)` ensures same-org membership row when set.  
Active-membership / role validation for assign/reassign is **documented for B1.7.3 RPCs** (not weakly enforced here).

---

## 17. Evidence contract

`evidence jsonb not null default '{}'::jsonb` with `jsonb_typeof(evidence) = 'object'`.  
Deep key/kind validation remains server-side in B1.7.3, aligned to B1.7.1 `AttentionSignalEvidence`.

---

## 18. Signal immutability (remediated)

| Layer | Behavior |
| --- | --- |
| Trigger | `BEFORE UPDATE` raises `attention signals are immutable` |
| DELETE trigger | **Not** used (remediation) so org/item `ON DELETE CASCADE` and local admin reset remain possible |
| Application DELETE | Denied by `REVOKE ALL` from `anon`/`authenticated` + RLS enabled with **no** policies |
| Product path | B1.7.3 may append Signals only; never UPDATE |

---

## 19. Organization consistency

- Item FK: `(organization_id, enrollment_id, customer_id, program_id)` → `enrollments` participation tuple (`ON DELETE RESTRICT`)
- Signal FK: `(organization_id, attention_item_id, enrollment_id)` → Item unique tuple (`ON DELETE CASCADE` for admin/org cleanup only)
- Signal enrollment FK: `(organization_id, enrollment_id)` → enrollments
- Member FKs always include `organization_id`

Cross-tenant Item/Enrollment/Signal combinations are FK-denied.

---

## 20. Enrollment relation

Release-1 source is Enrollment only. Customer/Program context is derived via the participation tuple columns required for composite integrity — not as alternate Attention sources.

---

## 21. Deduplication / concurrency

Partial unique index `attention_items_nonterminal_dedupe_uidx` on `(organization_id, enrollment_id, dedupe_key)` where `status in ('open','acknowledged')`.

- Duplicate open/acknowledged denied
- Terminal history does not block a new open Item
- Other org / enrollment / key allowed

Canonical key shape documented on column comment (B1.7.1 builder).

## 31. Rollback and incident contract

- **Local failed migration:** `supabase db reset` rebuilds from migration history (objects are additive).
- **New objects only:** Attention tables, indexes, trigger/function, comments. Existing tables untouched.
- **Pre-production rollback:** drop new Attention objects only after review; do not rewrite historical migrations once shared.
- **After any production data:** no casual DROP migration; require explicit incident plan.
- **Next phase** reviews any schema deltas before operational RPCs.
