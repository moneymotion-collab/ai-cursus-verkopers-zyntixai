## 2. Problem statement

B1.7.5 delivers a safe read-only Attention list and detail experience. The backend foundation for multiple lifecycle mutations already exists (B1.7.3 RPCs; B1.7.4 adapters, schemas, and error normalization), but operators cannot yet execute those actions safely from product UX.

Without a formal lifecycle UX contract there are risks around:

- UI permissions drifting from server permissions;
- duplicate submits;
- stale detail data;
- unsafe assignment targets;
- missing confirmation for destructive/terminal actions;
- raw RPC errors in the UI;
- existence leaks;
- inconsistent audit and refresh behavior;
- unclear list-versus-detail action boundaries;
- unauthorized expansion into deferred lifecycle features (reopen, restore, snooze, priority, Close-as-status).

---

## 3. Goal and user value

B1.7.6 must deliver a tenant-safe, role-aware, auditable, and accessible lifecycle experience so authorized operators can, on existing Attention items:

- acknowledge;
- assign;
- unassign;
- update severity;
- resolve;
- dismiss;
- archive when allowed.

Every product action must:

- use the same server authorization as the existing RPC;
- await an authoritative server result;
- cause the matching audit/event record via the existing RPC path;
- limit duplicate submits;
- provide safe pending, success, and error feedback;
- refresh the detail read authoritatively after success;
- avoid leaking hidden record or tenant information.

## 5. In-scope actions

The following actions are contractually in scope for B1.7.6 under existing backend conditions.

### 5.1 Acknowledge

- Only from status `open`.
- New status: `acknowledged` (acknowledgement is a **status**, with `acknowledged_at`).
- Authorized: owner, admin, staff.
- Viewer remains read-only.
- No destructive confirmation required.
- Explicit submit required.
- Server result remains authoritative.
- Already-acknowledged uses existing idempotent backend semantics (no-op return).

### 5.2 Assign and Unassign

- Assignment does **not** change lifecycle status.
- Authorized: owner, admin, staff.
- Target must be an **active** membership in the **same** organization.
- `null` means unassign.
- Same assignee may be treated as safe no-op.
- No cross-tenant or suspended target.
- No multi-assignee.

### 5.3 Update Severity

- Only existing severity values: `low` | `medium` | `high` | `critical`.
- Authorized: owner, admin, staff.
- Does not change lifecycle status.
- Same severity uses existing no-op semantics.
- No free-text severity.
- No priority semantics.

### 5.4 Resolve

- Only from non-terminal and non-archived state.
- Authorized: owner, admin, staff.
- New status: `resolved`.
- Resolution reason required per existing schema/RPC.
- Confirmation required.
- Produces existing `status_changed` event via RPC.

### 5.5 Dismiss

- Only from non-terminal and non-archived state.
- Authorized: owner, admin, staff.
- New status: `dismissed`.
- Dismissal reason required per existing schema/RPC.
- Confirmation required.
- Produces existing `status_changed` event via RPC.

### 5.6 Archive

- Only for terminal items (`resolved` | `dismissed` | `expired`).
- Only owner and admin.
- Staff and viewer must not see Archive.
- Confirmation required.
- Already archived remains a server error per existing semantics.
- Archive does **not** change lifecycle status (`archived_at` orthogonal).
- Archived visibility remains per existing permissions.

Not allowed on the list workspace:

- acknowledge buttons;
- assignment controls;
- severity controls;
- resolve or dismiss buttons;
- archive controls;
- overflow menus with lifecycle actions;
- bulk selection;
- keyboard shortcuts for mutations;

The list remains limited to:

- navigation;
- filtering;
- sorting;
- pagination;
- summary;
- access to detail.

This boundary reduces permission, stale-state, confirmation, and accessibility complexity.

## 8. Binding architecture

Use only:

```text
Attention detail UI
  → framework server action
  → B1.7.6 application action boundary
  → existing B1.7.4 Attention RPC adapter
  → existing authorized RPC
  → database mutation + append-only event
  → authoritative read refresh
  → updated read-only detail presentation
```

Not allowed:

```text
client component → Supabase RPC
client component → database
UI → own authorization
UI → direct mutation adapter
UI → unvalidated organization id
UI → unvalidated item id
UI → optimistic final state without server result
UI → manually write event records
UI → mutate then apply a non-authoritative local patch
```

Reuse existing repository patterns for `"use server"` actions, Zod boundaries, safe return, normalized errors, pending state, confirmation, server refresh/redirect, and accessibility feedback.

Do **not** introduce a new generic mutation framework.

## 9. Server actions and application boundary

B1.7.6 may add server actions on top of existing adapters.

Each server action must:

1. obtain authenticated server context;
2. resolve organization context safely;
3. validate input via existing or feature-scoped Zod schemas;
4. call only the existing Attention adapter;
5. not trust UI authorization;
6. return normalized Attention errors;
7. never leak raw RPC or database errors;
8. reject open redirects;
9. after success, refresh the authoritative Attention read;
10. be testable without a browser.

Server actions must not duplicate existing RPC semantics.

## 10. Action visibility matrix

### Owner and admin

May see, when item status and archive-state allow:

- Acknowledge;
- Assign / Unassign;
- Severity;
- Resolve;
- Dismiss;
- Archive (terminal items only).

### Staff

May see, when item status and archive-state allow:

- Acknowledge;
- Assign / Unassign;
- Severity;
- Resolve;
- Dismiss.

Staff must **not** see Archive.

### Viewer

Viewer sees **no** lifecycle controls.

### General rules

- Visibility is at most equal to server permission.
- The server remains authoritative.
- A hidden control is not a security boundary.
- Archived items show no mutation controls.
- Terminal items show no status-mutation controls (acknowledge / resolve / dismiss).
- Assignment and severity controls are available only within existing non-terminal / non-archived backend rules.
- Action visibility must not reveal that a hidden record or permission exists elsewhere.

Use existing Attention permission helpers where possible (`resolveAttentionPermissions` and related).

Statuses remain: `open` | `acknowledged` | `resolved` | `dismissed` | `expired`.

| Current status | Action | New status | Roles | Event | Confirmation | Idempotent |
| --- | --- | --- | --- | --- | --- | ---: |
| open | Acknowledge | acknowledged | o/a/s | status_changed | no | yes |
| open / acknowledged | Resolve | resolved | o/a/s | status_changed | **yes** | yes |

| open / acknowledged | Update severity | unchanged | o/a/s | severity_changed | no | yes |
| terminal | Archive | unchanged + archived_at | o/a | archived | **yes** | already-archived → error |
| terminal | status mutations | — | — | — | — | denied |
| archived | any mutation | — | — | — | — | denied |
| any | Close / Reopen | — | — | — | — | **out of scope** |

## 13. Assignment target contract and readiness gate

Assignment is allowed only when a safe source of eligible targets exists.

An eligible target must:

- have membership in the same organization;
- have membership status `active`;
- supply a valid existing member id;
- not come from another tenant;
- not be suspended or deleted.

The UI must not:

- offer free UUID entry;
- trust arbitrary client input as member id;
- use a general cross-organization people search;
- authorize a full membership list client-side.

### Readiness gate for B1.7.6-C

Before implementing Assignment UX, prove that an existing authorized server/application read capability can supply active same-organization memberships for the picker (reuse proven domain patterns such as Tasks/Customers/Leads/Enrollments member option loaders where they already meet the security bar).

If that capability cannot be proven safely:

- do not change database or RPCs inside B1.7.6-C;
- do not build an unsafe picker;
- stop B1.7.6-C;
- report that a separate owner-approved read-foundation decision is required.

**Contract publication itself is not blocked by this gate.**

## 14. Confirmation contract

### No confirmation required

- Acknowledge;
- Assign;
- Unassign;
- Update Severity.

These still require: explicit submit; pending state; duplicate-submit prevention; success or error feedback.

### Confirmation required

- Resolve;
- Dismiss;
- Archive.

Confirmation must:

- name the action clearly;
- identify the item safely without sensitive data;
- describe consequences;
- include the required reason for Resolve and Dismiss;
- be keyboard operable;
- manage focus safely;
- support cancel;
- perform no mutation before explicit confirmation.

Reuse existing repository patterns for confirmation pages, forms, or dialogs.

---

## 15. Pending, duplicate-submit, and refresh contract

Every action UX must:

- disable submit while pending;
- announce pending status understandably;
- limit repeated client submits;
- not show a definitive optimistic final state;
- await the server result;
- after success, refresh the authoritative detail read;
- refresh the event timeline after success;
- for an idempotent no-op, show a safe consistent result state.

Database row-lock and existing no-op semantics remain authoritative.

---

## 16. Concurrency and stale-data contract

- Existing RPCs use row locking (`FOR UPDATE`).
- There is no client-visible version token.
- B1.7.6 introduces **no** new optimistic concurrency token without separate owner approval.
- The UI must not invent its own stale-detection protocol.
- After every mutation, re-read authoritative server state.
- When the server rejects a mutation because status has already changed, show a safe conflict or refresh message.
- The user can then review the current detail state.
- A failure must never be presented as success.

This is **not** full optimistic concurrency control.

---

## 17. Error and result contract

Distinguish at least:

- validation error;
- authentication required;
- organization required;
- uniform unavailable;
- permission denied;
- invalid transition;
- invalid assignment target;
- archived or terminal restriction;
- duplicate / no-op success per existing semantics;
- recoverable server error;
- conflict / stale state insofar as server results support it.

Hard rules:

- use existing `normalizeAttentionError` semantics;
- no raw RPC error;
- no SQL details;
- no function names;
- no tenant or record existence leak;
- no hidden actor or membership information;
- field errors shown at the related field;
- general errors get an accessible error summary;
- success copy claims only what the server confirmed.

---

## 18. Audit and event requirements

Every real mutation must, via the existing RPC:

- update the item;
- write an append-only event in the same transaction;
- record the actor;
- respect organization context;
- record relevant before/after status, severity, or assignment;
- record timestamp;
- record reason when the contract requires it.

The UI must not:

- write a separate event;
- construct audit payloads;
- display raw event metadata;
- claim success when authoritative refresh does not show updated state.

---

## 19. Accessibility contract

Lifecycle controls must at minimum provide:

- clear action names;
- correct button semantics;
- no clickable divs;
- visible focus;
- keyboard operation;
- understandable pending text;
- `aria-live` only where appropriate;
- errors semantically associated with fields;
- keyboard-operable confirmation;
- focus after cancel and success per existing patterns;
- status and severity not by color alone;
- reason fields with label, help text, and validation;
- assignment picker with label and understandable option copy;
- no focus trap;
- no unexpected automatic submit;
- mutation feedback understandable without color.
