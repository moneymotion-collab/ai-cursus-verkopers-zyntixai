## 1. Executive Summary

Beta 1’s documented critical product sequence is:

```text
Program → Enrollment → Progress → Attention → Next Best Action
```

B1.1–B1.4 closed authentication, onboarding and first-value CRM guidance. B1.5 delivered the user-facing Programs and Enrollments workspaces on a proven PE database foundation and closed production verification with conditions.

**What remains missing for the next sequence step** is the **user-facing Progress Workspace**: typed application foundation, routes, list/detail/create/void/correction UX, navigation, Enrollment/Program contextual integration, automated tests, browser QA and production verification.

**Proven Progress technical foundations already exist** (`enrollment_progress_facts`, `record_progress_fact`, `void_progress_fact`, RLS, indexes, generated types). They **must not** be re-invented. B1.6 reuses them through membership-scoped server adapters and role-aware UI.

**Hard limits for B1.6:**

1. Progress is an **append-oriented fact ledger** (record / void / correction), not a free-form row editor and not an invented enrollment “health score”.
2. **No AI, Attention, Next Best Action, churn, notifications, certificates, billing, or member portal** in B1.6.
3. **No new Progress migrations** unless a proven blocker is documented in a remediation subphase.
4. Client-supplied organization IDs never authorize alone.
5. Laptop implementation starts only after publication + sync + **PARALLEL PASS**.

## 5. Actors and Roles

Roles are existing organization membership roles. There is **no** separate “enrolled member portal” actor in B1.6.

Authorization **source of truth** is the database (RPC + RLS). Application permission helpers are convenience hints only.

### 5.1 Proven DB mutation matrix (`record_progress_fact` / `void_progress_fact`)

| Role | Record manual fact | Correction record | Void fact | Notes |
| --- | --- | --- | --- | --- |
| owner | Yes | Yes | Yes | Manual only on enrollment status `active`/`paused`; correction/void also allowed on `completed`/`cancelled` (non-archived) |
| admin | Yes | Yes | Yes | Same as owner |
| staff | Yes | Yes | Yes | Manual **and** correction/void only when enrollment status ∈ `active`,`paused` |
| viewer | No | No | No | `insufficient role` |

Additional proven guards:

- Active organization membership required (`private.get_program_enrollment_actor_membership`).  
- Archived enrollment → treated as not found for mutations.  
- `occurred_at` not more than ~5 minutes in the future; not before `enrolled_at`.  
- Minimum payload required (title/description/numeric/`is_complete`/`sequence_number`).  
- Idempotency keys supported; correction requires idempotency key.  
- Lineage immutable; correction acyclic; one active correction per predecessor.

### 5.2 Proven DB read matrix (RLS)

| Role | Non-voided facts on non-archived enrollment | Voided facts | Archived enrollment facts |
| --- | --- | --- | --- |
| owner | Yes (`select_admin` / membership) | Yes (`enrollment_progress_facts_select_admin`) | Yes via admin policy (admin SELECT does not require non-archived) |
| admin | Yes | Yes | Yes via admin policy |
| staff | Yes (`select_member`: non-voided + non-archived enrollment) | No (member policy requires `voided_at is null`) | No via member policy |
| viewer | Yes (same member policy) | No | No |

Application UI **must not** promise voided-fact visibility to staff/viewer.

### 5.3 Explicitly forbidden actor actions

- Customer/lead “self check-in” without org membership.  
- Viewer record/void/correct.  
- Any direct table INSERT/UPDATE/DELETE from the authenticated client.  
- Trusting browser-supplied `organizationId` as authority.  
- Escalating staff rights to completed/cancelled enrollment mutations (DB forbids).

## 9. Domain and Lifecycle Contract

### 9.1 What a Progress record means

A **progress fact** is an append-oriented, organization-scoped observation about participation on a specific Enrollment (and its immutable participation tuple: customer + program). It is not an Enrollment status transition and does not replace Enrollment lifecycle RPCs.

### 9.2 Relationships

```text
Organization
  └── Enrollment (organization_id, id, customer_id, program_id)
        └── enrollment_progress_facts (same tuple FK)
```

Facts always copy `customer_id`/`program_id` from the enrollment at record time (RPC). Clients must not supply alternate customer/program IDs to “retarget” a fact.

### 9.3 Allowed mutation operations (only)

| Operation | Mechanism | Effect |
| --- | --- | --- |
| Record | `record_progress_fact` without correction id | Insert `source=manual` |
| Correct | `record_progress_fact` with `p_corrected_from_fact_id` | Void predecessor with system reason + insert `source=correction` |
| Void | `void_progress_fact` | Soft-revoke without replacement |

**Forbidden:** generic UPDATE of fact payload; DELETE; inventing new sources beyond `manual`/`correction`; client-side void without reason.

### 9.4 Enrollment status interaction (proven RPC rules)

| Enrollment state | Manual record | Staff correction/void | Owner/Admin correction/void |
| --- | --- | --- | --- |
| `pending` | No | No | No |
| `active` | Yes | Yes | Yes |
| `paused` | Yes | Yes | Yes |
| `completed` | No | No | Yes |
| `cancelled` | No | No | Yes |
| archived (`archived_at` set) | No (not found) | No | No |

Enrollment status changes remain **Enrollment** workspace concerns. Progress UI must fail closed when RPC rejects status.

### 9.5 Percentage / completion rules

- Fact-level `is_complete` is optional boolean payload — display when present.  
- Fact-level `numeric_value`/`numeric_unit` optional — display when present; unit requires value (DB).  
- **No** B1.6 canonical “enrollment progress %” derived product metric.  
- List/detail may show **counts** of active facts by type as informational only, clearly not a health score.

### 9.6 Timestamps and history

- `occurred_at`: user-meaningful event time (validated).  
- `recorded_at`: server default now.  
- Void metadata: `voided_at`, `voided_by_member_id`, `void_reason`.  
- Correction lineage: `corrected_from_fact_id` + `source=correction`.  
- There is **no** separate `progress_status_history` table; the fact ledger **is** the audit trail.

### 9.7 Idempotency

Honor RPC idempotency semantics (return existing active fact for same org/enrollment/source/key; error if key consumed by voided row). UI should generate stable keys for correction submits and optional manual retries.

### 9.8 Validation and safe failures

Map RPC exceptions to user-safe messages (pattern: Programs/Enrollments `normalize-*-error`). Foreign/missing IDs collapse to not-found / permission-denied shapes that do **not** enable cross-tenant enumeration. Prefer generic not-found over leaking existence across tenants.

## 10. Security Contract

### 10.1 Hard requirements

1. Resolve organization from **authenticated active membership** (page/org helpers), never from client trust alone.  
2. Pass membership-resolved `organizationId` into RPC adapters.  
3. Treat RLS as last line of defense; server actions still enforce role hints + fail closed.  
4. No `service_role` client in Progress feature code.  
5. No direct writes to `enrollment_progress_facts` from app code — RPC adapters only.  
6. Validate UUIDs and enums (fact types, sources) before RPC.  
7. Prevent privilege escalation (viewer mutation CTAs absent; direct URL posts fail closed).  
8. Do not authorize Progress access solely because a user knows an enrollment/program UUID.  
9. Collapse cross-tenant probes to safe not-found/deny.  
10. No secrets, tokens, emails, or raw PII dumps in logs or committed docs.  
11. Fail closed on missing membership, inactive org, unknown role.  
12. Auditability via fact ledger fields; do not strip recorder/void metadata for roles allowed to see them.

### 10.2 Required security tests (minimum)

- Role matrix: owner/admin/staff/viewer record/void/correct allow/deny  
- Tenant isolation: org A cannot read/mutate org B facts  
- Archived enrollment mutation denial  
- Status gate tests matching RPC rules  
- Direct route protection for create/void/correct  
- RLS regression for select_admin vs select_member voided visibility  
- Adapter never uses browser org id as authority  
- Idempotency / double-submit safe behavior

## 11. UX Contract

### 11.1 Routes (required shape)

| Route | Purpose |
| --- | --- |
| `/progress` | Fact list (org-scoped) |
| `/progress/new` | Record fact (owner/admin/staff); support `?enrollmentId=` prefill |
| `/progress/[factId]` | Fact detail |
| `/progress/[factId]/void` | Void confirmation workflow (authorized roles) |
| `/progress/[factId]/correct` | Correction workflow (authorized roles) |

Nested-only designs without a top-level workspace are **rejected** by this contract (Progress is a workspace in the product sequence). Enrollment/Program pages integrate **to** Progress; they do not replace it.

### 11.2 Navigation

Primary nav order becomes:

```text
Home → Leads → Customers → Programs → Enrollments → Progress → Tasks
```

Update `src/components/app-shell.tsx` `activeNav` union accordingly. Extend `safe-return-path` allowlists for `/progress` and `/progress/...`.

### 11.3 List behavior

- Title: **Progress**  
- Explanation: record and review enrollment progress facts for this organization.  
- CTA: **Record progress** for owner/admin/staff.  
- Columns (minimum): occurred time; fact type; title/summary; enrollment/customer/program labels; source; voided indicator (owner/admin when viewing voided).  
- Filters: fact type; enrollment; customer; program; voided toggle (**owner/admin only**, default active-only).  
- Sort: `occurred_at` desc default.  
- Pagination: shared list pagination pattern.  
- Empty / no-results / loading / error: mirror PE lists.

### 11.4 Create / correct / void

- Create collects: enrollment (eligible), fact type, occurred_at, optional title/description/numeric/is_complete/sequence, optional idempotency key (server may generate).  
- Correct: load predecessor; require reason/payload per RPC; show that predecessor will be voided by correction semantics.  
- Void: require non-empty reason; confirm.  
- Success → fact detail. Failure → preserve input + user-safe error.

### 11.5 Detail

Show fact fields, void/correction lineage links, recorder label, enrollment/customer/program links, role-aware void/correct CTAs. Do not show Progress “score widgets”, NBA, or health.

### 11.6 Integration copy remediation

Replace Enrollment/Program detail **Progress deferred** placeholders with accurate Progress workspace guidance and links/CTAs when permitted. Do not re-introduce stale “later phase” claims for shipped Progress capabilities after integration ships.

### 11.7 Accessibility / responsive / terminology

- Accessible labels on forms and filters.  
- Mobile-usable list/detail/forms (same bar as PE).  
- Terminology: **Progress**, **progress fact**, **Enrollment**, **Program**, **Customer**, **void**, **correction** — consistent with CRM/PE. Avoid “delete”, “score”, “health”.

### 11.8 Safe redirects

Use allowlisted return paths only. Post-login return to `/progress*` must be safe-return validated.
