## 1. Executive Verdict

```text
BLOCKED
```

Independent QA reconfirmed that B1.1’s intended auth/routing behaviors, automated suites, typecheck, lint and build are largely correct and in scope. One **blocking security defect** was observed during browser verification and confirmed by DOM inspection:

**Auth forms default to HTML `method="get"` (no `method` attribute).** When the client submit handler does not run (failed/late hydration or non-JS submit), credentials are placed in the query string. During this QA run, a login attempt navigated to:

```text
/login?email=…&password=…
```

That violates the B1.1-QA requirement that password values must never be placed in URLs, and affects login plus the new B1.1 recovery forms (same pattern). Remediation requires a product-code change; QA does not implement fixes.

Production auth parity remains **UNVERIFIED** (expected; not the blocking reason).

## 7. Redirect Security Review

Authoritative utility: `resolveSafeReturnPath` (allowlist, not open-prefix matching of arbitrary paths).

| Input | Result (code + tests) |
| --- | --- |
| `/leads` | accept |
| `/customers?status=active` | accept |
| `/tasks#overdue` | pathname allowlisted; **hash stripped** (returns `/tasks`) |
| `https://evil.example` | reject |
| `//evil.example` | reject |
| `javascript:alert(1)` | reject |
| `data:text/html,test` | reject |
| `file:///etc/passwd` | reject (scheme) |
| `/%2f%2fevil.example` | reject |
| `/\\evil` | reject |
| empty / whitespace | reject → fallback |
| malformed `%zz` | reject |

Consumers: login page `next`, `resolvePostLoginDestination`, callback, middleware `next` construction for protected routes, recovery callback destination via app-built URL (not raw Host).

Fallback `/` (or `/register/complete` in callback) does not recurse into Auth loops in tested paths.

**Observation:** explicit tests for `file://` and fragment-stripping behavior are thin; behavior is still safe via scheme/allowlist logic.

## 17. Risks and Defects

### Blocking defects

1. **Auth forms omit `method="post"`** (login, register, forgot-password, reset-password). Native submit defaults to GET and can place email/password in the URL (observed during QA). Requires product-code fix before controlled production verification.

### Non-blocking observations

1. `resolveSiteOrigin` does not strictly validate http(s)-only origins / reject credentials or paths in `NEXT_PUBLIC_SITE_URL`.
2. Recovery detection depends on allowlisted `next=/reset-password`; misconfigured Auth templates could skip the reset page.
3. Reset page treats any authenticated session as eligible (not recovery-AMR exclusive).
4. Hash fragments are stripped from return paths.
5. First-error focus management is weak.
6. No automated test asserting form `method="post"`.
7. Journey F not browser-verified here.
8. Intermittent local HTTP 500 on cold probe.

### Production-only conditions

Listed in §16.

### Deferred scope

Onboarding, checklist, Programs/AI/Social, migrations, dashboard mutations — untouched and correctly deferred.
