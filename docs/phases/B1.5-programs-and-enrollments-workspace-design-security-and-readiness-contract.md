## 1. Executive Summary

Beta 1’s critical product sequence is:

```text
Program → Enrollment → Progress → Attention → Next Best Action
```

B1.1–B1.4 closed authentication, onboarding and first-value CRM guidance. Leads, Customers and Tasks workspaces already exist. Programs & Enrollments already have a **complete database foundation** (tables, history, RPCs, RLS, open-participation uniqueness, lifecycle invariants). What is missing is the **user-facing Programs & Enrollments Workspace**: typed application foundation, routes, list/create/detail/edit/lifecycle/archive UX, navigation, Customer/Program contextual integration, automated tests, browser QA and production verification.

Progress technical foundations (`enrollment_progress_facts`, `record_progress_fact`, `void_progress_fact`) exist but **must not** be productized in B1.5.

### 6.2 `program_status_history`

- Archive only when terminal: `enrollments_archive_terminal_only_check`

## 10. Domain Definitions

### 10.1 Program

A **Program** is an organization-scoped educational or coaching trajectory definition (table comment). It is not a customer instance and not a progress record.

**Required fields on create:** `name`, `delivery_mode`.  
**Optional:** `description`, `metadata` (object).  
**System-set:** `status='draft'`, `created_by_member_id`, timestamps.

**Delivery mode (canonical product labels — DB values unchanged):**

| DB value | Product label |
| --- | --- |
| `self_paced` | Self-paced |
| `cohort` | Cohort |
| `group_coaching` | Group coaching |
| `one_to_one` | One-to-one |
| `membership` | Membership |
| `hybrid` | Hybrid |

**Editable after create (non-archived):** name, description, delivery_mode, metadata via `update_program`.  
**Not editable via update RPC:** status (use transition), archive flag (use archive/restore), organization id, created_by.

**Active vs archived:** `archived_at` is orthogonal soft-archive and does **not** change lifecycle status. Staff/viewer cannot see archived programs via member SELECT; owner/admin can.

**Relationship to enrollments:** one program has many enrollments; archive blocked while open enrollments exist.

### 10.2 Enrollment

An **Enrollment** is an organization-scoped participation instance linking **one Customer** to **one Program**.

**Required on create:** `customer_id`, `program_id`.  
**Optional:** `owner_member_id`, `initial_status` (`pending` default or `active`), `metadata`.  
**Source for public create:** must be `manual` (RPC rejects other public sources).

**Immutable after create:** `customer_id`, `program_id`, `organization_id`, `source`, `created_by_member_id`.  
**Editable after create (non-archived):** `owner_member_id`, `metadata` only (no `update_enrollment` RPC).  
**Lifecycle:** via `transition_enrollment_status` only.

**Open / active enrollment definition (canonical):** status ∈ `pending`, `active`, `paused` **and** `archived_at is null`. This matches the unique index and archive-program open count.

**Terminal states:** `completed`, `cancelled`. Only terminals may be archived/restored.

**Dates:** `enrolled_at` set on create; `started_at` / `completed_at` / `cancelled_at` maintained by transition milestones. No expected-end-date field exists.

## 11. Program Lifecycle

**States:** `draft` → `active` ↔ `paused`; any of draft/active/paused → `retired`; `retired` → `active` only.

Exact allowed transitions (`private.is_allowed_program_status_transition`):

| From | To |
| --- | --- |
| `draft` | `active`, `retired` |
| `active` | `paused`, `retired` |
| `paused` | `active`, `retired` |
| `retired` | `active` |

Same-status transitions are rejected. Archived programs cannot transition.

**Archive:** owner/admin; fails with open enrollments (`pending|active|paused` & not archived).  
**Restore:** clears `archived_at`; does not change status.

**History:** every transition writes `program_status_history` (create writes `null → draft`).

**Canonical product terms:** use **Retired** for lifecycle `retired`; use **Archived** only for soft-archive. Do not rename DB values.

---

## 12. Enrollment Lifecycle

Exact allowed transitions:

| From | To |
| --- | --- |
| `pending` | `active`, `cancelled` |
| `active` | `paused`, `completed`, `cancelled` |
| `paused` | `active`, `completed`, `cancelled` |

`completed` and `cancelled` have **no** outbound transitions.

**Pause / resume:** `active → paused` and `paused → active`.  
**Complete / cancel:** from `active` or `paused` (cancel also from `pending`).  
**Reason:** optional `p_reason` on transition (stored on history). No separate pause-reason column.

**Archive / restore:** owner/admin; terminal statuses only; restore does not reopen to non-terminal status.

**History:** create and every transition write `enrollment_status_history`.

## 14. Navigation Decision

**Decision: mixed primary navigation — both Programs and Enrollments in main app shell nav.**

Rationale:

1. Critical Beta 1 sequence requires discoverable Program and Enrollment surfaces.
2. Existing shell is a flat peer nav (Leads / Customers / Tasks) with no “More” menu.
3. Contextual-only Enrollments would hide the workspace from operators who start from Programs or global ops work.

**Exact nav order (recommended):**

```text
Home · Leads · Customers · Programs · Enrollments · Tasks
```

**Also required contextual entry points:**

- Customer detail → enrollment summary + “Add enrollment” + links to enrollment/program detail
- Program detail → enrollment preview + “Enroll customer” + link to filtered `/enrollments?program=`

**Implementation dependency:** extend `AppShell` `activeNav` union and links; extend `isProtectedApplicationPath` and `isAllowlistedPathname` for `/programs` and `/enrollments` families; reuse onboarding enforcement helpers used by Leads/Customers/Tasks.

## 15. Programs UX Contract

### 15.1 List (`/programs`)

- **Title:** Programs  
- **Explanation:** Define and manage coaching/education trajectories for this organization.  
- **CTA:** “New program” for owner/admin.  
- **Columns / fields:** Name; Delivery mode; Status; Active enrollment count (open definition); Updated date; Archived indicator for owner/admin when viewing archived.  
- **Search:** name (case-insensitive trim match).  
- **Filters:** status; delivery_mode; archived toggle (owner/admin only, default active-only).  
- **Sort:** updated_at desc default; allow name / status.  
- **Pagination:** reuse shared `Pagination` component; org-scoped counts only.  
- **Empty:** “No programs yet” + create CTA.  
- **No results:** “No programs match these filters” + clear filters.  
- **Row nav:** to detail.  
- **Archive/restore:** from detail (and optionally row actions for owner/admin) with confirmation.

### 15.2 Create / Edit form

| Field | Required | Rules |
| --- | --- | --- |
| Name | Yes | Non-empty trimmed; unique among non-archived programs in org |
| Delivery mode | Yes | One of six allowed values |
| Description | No | Trimmed; empty → null |
| Metadata | No | Default `{}`; no free-form admin JSON UI required in B1.5 — omit advanced metadata editor unless needed for parity; pass `{}` |

Defaults: delivery mode no silent invalid default — require explicit selection. Submit via server action → `create_program` / `update_program`. Cancel returns to list or detail. Duplicate name → user-safe conflict message. Success → program detail.

### 15.3 Detail

Show: name, status, delivery mode, description, created/updated, archived badge, open enrollment count, preview of recent open enrollments, link to filtered enrollment list, lifecycle action buttons (allowed transitions only), Edit, Archive/Restore, status history timeline.  
**Progress boundary:** optional static note “Progress tracking comes in a later phase” — **no progress widgets, facts, or RPCs**.

## 16. Enrollments UX Contract

### 16.1 List (`/enrollments`)

- **Title:** Enrollments  
- **Explanation:** Track customer participation in programs.  
- **CTA:** “New enrollment” for owner/admin/staff.  
- **Fields:** Customer; Program; Status; Owner; Enrolled date; Updated; Archived (role-aware).  
- **Search:** customer name / program name (via joins or pre-resolved labels — must remain org-scoped).  
- **Filters:** status; program; customer; owner; archived toggle (owner/admin).  
- **Sort:** enrolled_at / updated_at desc default.  
- **Pagination:** shared component.  
- **Empty / no-results / loading / error:** mirror CRM lists.

### 16.2 Create flow

1. Select eligible customer (not archived; status `onboarding` or `active`).  
2. Select eligible program (not archived; status `active`).  
3. Optional owner (active org member).  
4. Initial status: `pending` (default) or `active`.  
5. Submit → `create_enrollment`.  

Handle: duplicate open enrollment; ineligible customer/program; invalid owner; permission failure — mapped user-safe errors. Success → enrollment detail. Prefill from query (`?customer=`, `?program=`) when coming from contextual CTAs.

### 16.3 Detail

Customer identity + link; Program identity + link; status; owner; enrolled/started/completed/cancelled timestamps; lifecycle controls; history; archive/restore when eligible.  
**Progress boundary:** placeholder text only — no check-ins, milestones UI, health/churn, NBA.

### 16.4 Edit and transitions

- **Edit page:** owner assignment + (optional minimal) notes via metadata **only if** a simple notes key is defined; otherwise owner-only edit is enough for B1.5. Prefer owner reassignment form without inventing metadata schema.  
- **Transitions:** dedicated controls listing **only allowed** next statuses; optional reason; confirm for terminal cancel/complete.  
- **UI behavior:** confirmed server actions (no optimistic status that can diverge from DB). Invalid transition → preserve form, show error.

## 20. Tenant-Isolation Contract

### Principles (binding)

1. Organization context comes from authenticated membership resolution (same pattern as Leads/Customers/Tasks).  
2. Browser-submitted organization IDs must never grant access without membership proof.  
3. Program/Enrollment reads are membership scoped (RLS).  
4. Writes are role scoped (RPC / limited UPDATE).  
5. Customer and program eligibility verified in `create_enrollment` (DB).  
6. Owner assignment limited to active same-org members (DB validate + trigger).  
7. Cross-organization identifiers fail closed.  
8. Archived visibility follows existing admin-vs-member policies.  
9. History remains tenant scoped.  
10. Direct routes must not bypass permissions.  
11. Pagination/filters must not leak cross-tenant counts or rows.

### Proven vs missing

| Layer | Status |
| --- | --- |
| Database RLS + RPC auth | Proven |
| Application loaders/actions for PE | Missing — required in B1.5 |
| Protected route middleware coverage for PE paths | Missing — required in B1.5.1 |
| Safe return allowlist for PE paths | Missing — required in B1.5.1 |

### Negative tests required

Cross-org list/detail; foreign UUID detail; staff archive denial; viewer create denial; duplicate open enrollment; archived/ineligible customer/program create; archive program with open enrollments; transition archived enrollment; owner assignment to other-org member.

**Migration severity:** no PE RLS gap found that blocks UI start. UI may begin once app-layer enforcement mirrors DB. If a live gap is discovered, stop and document remediation — do not silently add SQL in a UI subphase.

**Boundaries:**

| --- | --- |

| Idempotency | Duplicate create → conflict error; archive already-archived → stable user error |
| Concurrency | RPC `FOR UPDATE`; surface conflict/not-found safely |

**Do not** put service-role keys in client bundles. **Do not** call progress RPCs from B1.5 UI.
