## 3. Official title and user goal

**Title:** B1.6.3 — Controlled Progress Mutations

**User goal (testable):** An authorized organization member (owner/admin/staff per RPC + app permission matrix) can **record** a manual progress fact, **void** an eligible fact with a reason, or **correct** an eligible fact (record with `correctedFromFactId` + required idempotency key), then see list/detail refresh reflecting the ledger change. Viewer and unauthenticated users cannot mutate. Generic field UPDATE, DELETE, restore-from-void, and PE deferral remediations remain out of scope.

**Primary journey:** Progress list/detail → authorized CTA → create / void confirmation / correct form → server action → RPC → redirect or detail refresh with success/error feedback.

**Primary users:** Owner, Admin, Staff (mutate within status gates); Viewer (read-only).

## 5. Mutation inventory and classification

| Candidate mutation | Classification | Evidence |
| --- | --- | --- |
| Record manual fact | **SUPPORTED BY EXISTING CONTRACT** | `record_progress_fact` without `p_corrected_from_fact_id` |
| Correct fact | **SUPPORTED BY EXISTING CONTRACT** | Same RPC with `p_corrected_from_fact_id` + idempotency key; voids predecessor atomically |
| Void fact | **SUPPORTED BY EXISTING CONTRACT** | `void_progress_fact(org, fact_id, reason)` |
| Restore voided fact | **OUT OF B1.6.3 SCOPE** | No restore RPC; void is soft-revoke without reverse path |
| Delete fact | **OUT OF B1.6.3 SCOPE** / **SECURITY BLOCKED** | No DELETE grant; no delete RPC |
| Generic UPDATE of payload | **OUT OF B1.6.3 SCOPE** / **SECURITY BLOCKED** | Explicitly forbidden; `PROGRESS_UNSUPPORTED_RPC_NAMES.update`; authenticated UPDATE revoked |
| Change recorder | **OUT OF B1.6.3 SCOPE** | Recorder set by RPC membership actor |
| Change Enrollment/Program link on existing fact | **OUT OF B1.6.3 SCOPE** | Tuple copied at record time; lineage immutable |
| Change occurred_at via edit | **OUT OF B1.6.3 SCOPE** | Only via new record/correct payload, not UPDATE |
| Archive Progress fact | **OUT OF B1.6.3 SCOPE** | Not a Progress concept; enrollment archive blocks mutations |
| Free-form history note table | **OUT OF B1.6.3 SCOPE** | Ledger fields are the audit trail |

### 5.1 RPC contracts (proven)

#### `public.record_progress_fact` — SECURITY DEFINER

| Item | Contract |
| --- | --- |
| Params | `p_organization_id`, `p_enrollment_id`, `p_fact_type`, `p_occurred_at`, optional title/description/numeric/unit/is_complete/sequence/idempotency/corrected_from |
| Returns | `uuid` (fact id) |
| Auth | `auth.uid()` required; active membership via `private.get_program_enrollment_actor_membership` |
| Roles | owner/admin/staff; viewer → `insufficient role` |
| Tenant | Organization must be active; enrollment loaded in org |
| Side effects | Insert manual **or** void predecessor + insert correction; customer/program copied from enrollment |
| Idempotency | Unique `(org, enrollment, source, key)`; return existing active fact; error if key on voided row |
| Errors (examples) | not authenticated; active membership required; insufficient role; organization not found; invalid fact type/payload; enrollment status/archive gates; correction lineage conflicts |

#### `public.void_progress_fact` — SECURITY DEFINER

| Item | Contract |
| --- | --- |
| Params | `p_organization_id`, `p_progress_fact_id`, `p_reason` |
| Returns | `void` |
| Auth / roles | Same membership gate; viewer denied |
| Effect | Sets `voided_at`, `voided_by_member_id`, `void_reason` |
| Guards | Fact must exist in org; not already voided; enrollment not archived; status gates by role |
| Errors | progress fact not found; already voided; enrollment not found; status does not allow progress |

### 5.2 App permission overlay (must align with RPC)

| Role | Manual record | Correct | Void |
| --- | --- | --- | --- |
| owner / admin | Enrollment `active`/`paused`, non-archived | Also `completed`/`cancelled`, non-archived, non-voided predecessor | Same as correct eligibility |
| staff | `active`/`paused` only | `active`/`paused` only | `active`/`paused` only |
| viewer | No | No | No |
| unauthenticated | Login redirect | Login redirect | Login redirect |

Server actions must resolve org membership and role server-side; UI visibility is hints only. RPC remains authoritative.

### UI states (required)

- Permission denied / insufficient role (safe copy)
- Unavailable / not-found (same copy as B1.6.2)

- Idempotency / correction conflict mapping via existing normalize layer
- Loading + disabled submit (no double submit)
- Success: redirect to detail (or list) + revalidate `/progress` and fact paths
- Destructive void confirmation before submit
- Correction must disclose predecessor will be voided by RPC semantics
- No optimistic ledger writes that diverge from RPC outcome

### Patterns to follow

Enrollment `"use server"` actions: resolve org → verify role → call mutation foundation → `revalidatePath` → return typed result (redirects may mirror Programs/Enrollments workflow forms). Prefer non-optimistic server round-trips.

## 9. Data integrity and transitions

| Rule | Contract |
| --- | --- |
| Allowed ops | Record, Correct, Void only |
| Voided | Soft; no restore in B1.6.3 |
| Correction | Requires idempotency key; voids predecessor with system reason; acyclic; one active correction per predecessor |
| Idempotent retry | Return existing active fact for same key when applicable |
| Timestamps | `recorded_at` / void timestamps set by DB; `occurred_at` client-supplied with RPC future-skew guard |
| Actor | `recorded_by_member_id` / `voided_by_member_id` from membership |
| Forbidden transitions | Edit-in-place; delete; restore; mutate voided fact except via new correction rules enforced by RPC |

If UI cannot express an invariant the DB already enforces, show mapped error — do not invent client-only bypasses.
