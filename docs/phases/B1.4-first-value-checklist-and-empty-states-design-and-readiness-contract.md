## 3. Objective

Help a newly onboarded organization reach its **first useful CRM outcome** after company setup:

1. Confirm company setup is complete (derived).
2. Create a first lead.
3. Create a first task.
4. Optionally notice the customer workspace via a soft link.

Improve the **Leads** empty state with a clear primary create action.

Do **not** expand into a dashboard, onboarding redesign, or multi-surface empty-state redesign.

## 5. Checklist Scope and Completion Rules

### 5.1 Required items

| ID | Label (user-facing intent) | Completion rule | Primary CTA |
| --- | --- | --- | --- |
| `company_setup` | Finish company setup | `organizations.onboarding_completed_at IS NOT NULL` for the **selected** organization | `/onboarding?org=<orgId>` only if incomplete (normally unreachable on `/leads` for incomplete owners) |
| `first_lead` | Add your first lead | Count of leads for selected org with `archived_at IS NULL` ≥ 1 | `/leads/new?org=<orgId>` (preserve existing create-href query conventions) |
| `first_task` | Create your first task | Count of tasks for selected org with `archived_at IS NULL` ≥ 1 | `/tasks/new?org=<orgId>` (preserve existing create-href query conventions) |

**Progress:** `completedCount / 3` using only the three required items above.

### 5.2 Archive rule (binding)

| Entity | May archived rows satisfy completion? | Basis |
| --- | --- | --- |
| Leads | **No** | Explicit B1.0 rule: non-archived leads only |
| Tasks | **No** | B1.0 says “count of tasks ≥ 1” without archive wording; product list defaults exclude archived (`includeArchived: false`). For a first **useful** outcome, only non-archived tasks count. **Resolved in this contract:** require `archived_at IS NULL`. |
| Customers | N/A for required completion | Soft link only |

Cancelled or completed **non-archived** tasks **do** count (they remain useful history and are not archived). Lead status (open / converted / lost / etc.) does **not** matter for first-lead completion as long as the row is non-archived.

### 5.3 Optional soft customer link

| Item | Rule |
| --- | --- |
| Purpose | Encourage discovery of `/customers` |
| Hard gate? | **No** — never blocks checklist completion or auto-hide |
| Counts toward progress? | **No** |
| Preferred CTA copy intent | “Review customer workspace” (or equivalent short soft wording) |
| Href | `/customers?org=<orgId>` |
| Visibility | Shown only while the checklist panel itself is visible |
| Completion tracking | None in B1.4 (no visit flag, no customer-count gate) |

### 5.4 Visibility matrix

The checklist panel is **visible** only when **all** of the following are true for the selected organization context on `/leads`:

1. User is authenticated.
2. Active membership exists for the selected organization.
3. Membership role is `owner` **or** `admin`.
4. `onboarding_completed_at IS NOT NULL`.
5. `first_run_checklist_dismissed_at IS NULL`.
6. At least one required item (`company_setup`, `first_lead`, `first_task`) is incomplete.

The checklist panel is **hidden** when any of the following is true:

| Condition | Result |
| --- | --- |
| Role is `viewer` | Hidden (no organization-management onboarding controls) |
| Role is `staff` | Hidden (staff may create CRM records via normal headers; checklist is owner/admin guidance) |
| Onboarding incomplete | Hidden on CRM surfaces (incomplete **owners** are already gated to `/onboarding`; non-owners are not checklist audience) |
| Dismissed (`first_run_checklist_dismissed_at IS NOT NULL`) | Permanently hidden for that org until support clears the timestamp |
| All three required items complete | Hidden even without dismiss |
| Auth / org-context failure panels | Checklist not rendered |

### 5.5 Dismiss behavior

| Rule | Requirement |
| --- | --- |
| Who may dismiss | Active `owner` or `admin` of the target organization |
| Who may not dismiss | `staff`, `viewer`, unauthenticated, non-members, other-tenant members |
| Persistence | Set `organizations.first_run_checklist_dismissed_at` to server `now()` on first successful dismiss |
| Idempotency | If already non-null, return success **without changing** the existing timestamp |
| Effect | Hides checklist; does **not** alter onboarding fields, lead/task data, or derived completion |
| Undo in product | **Not in B1.4** — support/manual clear only |
| Client trust | Never trust client-supplied org id without membership resolution |

### 6.1 Role summary

| Role | See checklist | Dismiss | See Leads empty “Add your first lead” CTA |
| --- | --- | --- | --- |
| `owner` | Yes (when §5.4 visible) | Yes | Yes (when unfiltered empty + create allowed) |
| `admin` | Yes (when §5.4 visible) | Yes | Yes |
| `staff` | No | No | Yes (create already allowed by lead permissions) |
| `viewer` | No | No | No |

### 6.2 Tenant isolation

1. Every lead/task count query must filter by the **resolved selected organization id**.
2. Dismiss write must target only that organization id after membership + role checks.
3. Foreign org ids must fail closed (`organization_not_found` / forbidden) with user-safe messages.
4. No service-role key in client bundles; no cross-tenant selects/updates.
5. Prefer existing helpers: `resolveOrganizationContext` / `listActiveOrganizationMemberships` / onboarding org resolution patterns — do not invent a parallel membership model.

## 8. Write-Path Decision

### 8.1 Evidence

| Finding | Evidence |
| --- | --- |
| Dismiss column exists | `supabase/migrations/20260720140000_add_organization_first_run_onboarding.sql` |
| Column already selected into context | `read-onboarding-context.ts` / `OnboardingContext.firstRunChecklistDismissedAt` |
| Onboarding RPC does **not** set dismiss | RPC `UPDATE` sets name/enums/completion only; returns dismiss unchanged |
| Org UPDATE RLS | `organizations_update_admin`: `owner` **or** `admin` |
| Existing app `organizations.update` helper | **None found** under `src/` |

### 8.2 Chosen approach (binding preference)

```text
PREFERRED WRITE PATH:
Authenticated server action
  → auth.getUser()
  → resolve active membership for target organizationId
  → require role owner|admin
  → supabase.from('organizations')
       .update({ first_run_checklist_dismissed_at: <now or keep existing> })
       .eq('id', organizationId)
  → rely on organizations_update_admin RLS as defense in depth
```

Authorization requirements:

1. Server-only action (`"use server"`), same CSRF model as existing feature actions.
2. Membership resolution before write; never update by raw client org id alone.
3. Application-level role gate: owner/admin only (staff/viewer denied before update).
4. Idempotent read-then-write or equivalent: if dismiss already set, return success and preserve timestamp.
5. Update **only** `first_run_checklist_dismissed_at` (do not rewrite onboarding fields).
6. User-safe errors via a small normalizer (reuse onboarding/org error style where practical).

### 8.3 Migration / RPC decision

| Option | Decision |
| --- | --- |
| New migration | **Not expected / not allowed** unless preferred path is proven impossible |
| Extend `apply_organization_onboarding` | **Not preferred** — owner-only today; dismiss must allow admin; would require SQL change |
| New SECURITY DEFINER RPC | **Not preferred** — RLS already sufficient for owner/admin UPDATE |
| Direct table update via server action + RLS | **Chosen** |

If implementation discovers that column-level grants, triggers, or RLS unexpectedly block the update, stop and document a follow-up decision before adding SQL. Do not silently add migrations in B1.4 implementation without an explicit remediation record.

### 8.4 Read / derivation path

Prefer a small pure derivation helper (unit-testable) plus org-scoped count queries on `/leads` load (or a dedicated checklist loader invoked from the leads page loader). Reuse dismiss + onboarding completion from existing org read patterns; do not require the full onboarding wizard context for staff/viewer pages.

Counts must not depend on the current list page’s filters (a filtered-empty leads page must not mark `first_lead` incomplete if non-archived leads exist for the org).

## 13. Risks and Conditions

### Non-blocking

1. No existing `organizations.update` helper — B1.4 must add a narrow dismiss write carefully.
2. Admin can update orgs via RLS but cannot complete onboarding (owner-only RPC) — checklist intentionally allows admin dismiss/view while onboarding remains owner-gated.
3. Existing production orgs may already have leads/tasks; checklist should hide quickly when derived complete.
4. Production deployment parity is documented historically, not re-proven in this contract phase.

### Blocking for calling B1.4 “done”

1. Missing Leads unfiltered empty CTA for create-eligible roles.
2. Checklist visible to viewer/staff.
3. Cross-tenant dismiss or counts.
4. Non-idempotent dismiss that rewrites timestamps or errors on repeat.
5. Any change to onboarding Step 2 remediation behavior.
6. New migration/RPC without documented necessity.
